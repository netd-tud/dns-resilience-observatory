    How we measure and collect data

    Country data comes from APNIC Labs DNSSEC measurements. The country gauge presents the mean validation percentage across available country observations; indeterminate validation is shown as unknown.

    For recursive DNS resolver data, we send a simple A-record query for dnssec-failed.org to each known recursive DNS resolver. A SERVFAIL response indicates DNSSEC validation is enabled, while a NOERROR response indicates that it is not enabled. Non-replying recursive DNS resolvers are marked as unknown. dnssec-failed.org is a domain operated by COMCAST with a deliberately broken DNSSEC signature, so a validating resolver will reject the response.

    How we measure and collect data

    We run active QMIN measurements to observe the query-name sequence generated by each tested recursive DNS resolver. QMIN is classified as properly enabled when the measurement reports QMIN and no more than 10 minimization iterations are observed. More than 10 iterations is highlighted as a potential excessive-query and amplification risk. Measurements explicitly reporting no QMIN are classified as not implemented. Unstable means that repeated measurements produced different QMIN behavior; missing or otherwise inconclusive measurements are shown as unknown.

    max_minimise_count is the maximum number of minimization queries observed for a tested recursive DNS resolver, while minimize_one_lab records how many minimization steps reduced the query name by one label.

    The horizontal bars show the three most frequently observed values for max_minimise_count and minimize_one_lab across measured recursive DNS resolvers.

    How we measure and collect data

    CAIDA Spoofer measurements provide active evidence that a network allows or blocks packets with spoofed source addresses. A recursive DNS resolver is classified as allowing spoofing when its AS has allowing evidence, and as actively blocking when its AS has CAIDA blocking evidence but no conflicting allowing evidence. Resolvers without either classification are shown as unknown.

    In addition to CAIDA Spoofer data, we use a phenomenon in the open DNS infrastructure called transparent DNS forwarders. These are DNS servers that relay queries to upstream resolvers while retaining the original client's source address, hence forwarding packets with spoofed source IP addresses. The transparent forwarders found by the Open DNS API provide additional evidence that source-address validation is missing or not properly deployed in the AS of the transparent forwarder. More details on this component and the measurement method can be found in the following papers:

    • Transparent Forwarders: An Unnoticed Component of the Open DNS Infrastructure by Nawrocki et al. (ACM CoNEXT 2021)
    • Forward to Hell? On the Potentials of Misusing Transparent DNS Forwarders in Reflective Amplification Attacks by Koch et al. (ACM CCS 2025)
    !

    Important limitation: A resolver deployed in an AS with a transparent forwarder does not mean that the whole AS fails to implement source address validation (SAV). Only parts of the network where the transparent forwarder is deployed may allow source-address spoofing. Nevertheless, this is a strong indicator and influences the resilience score of the network.

    For each AS and economy represented by recursive DNS resolvers, we average the available MANRS readiness scores for anti-spoofing, coordination, filtering, IRR routing information, and RPKI routing information. Each AS or economy contributes equally to the displayed group average.

    Open and closed groups are based on whether an AS or economy contains at least one open or closed recursive DNS resolver. An AS or economy can therefore appear in both groups. Entity totals include all matching database entities.

    How we measure and collect data

    A recursive DNS resolver is classified as anycast when its IP address is covered by an observed anycast prefix using the MAnycast API. We report on the number of anycast sites by using the results from the MAnycast API extended with the data from the ODNS API. We can, again, leverage transparent DNS forwarders to identify additional anycast sites that are not covered by the MAnycast API. The authoritative nameserver used for the open DNS measurements returns the IP address of the connecting backend resolver. In the case of a transparent forwarder that relays its request to an anycast resolver such as Google's 8.8.8.8, the actual IP address of the anycast site is returned. For more information on transparent DNS forwarders, see the following publications:

    • Transparent Forwarders: An Unnoticed Component of the Open DNS Infrastructure by Nawrocki et al. (ACM CoNEXT 2021)
    • Forward to Hell? On the Potentials of Misusing Transparent DNS Forwarders in Reflective Amplification Attacks by Koch et al. (ACM CCS 2025)

    A recursive DNS resolver is classified as dual stack when the same resolver identity has at least one observed IPv4 address and at least one observed IPv6 address.     Protocols

    Port Distribution

    How we measure and collect data

    Protocol support is collected from the service records associated with each recursive DNS resolver. Only records with a successful protocol test contribute to the gauges and port distribution. A failed test is stored as not supported, while the absence of a protocol record means it has not been tested. Each ring independently shows the percentage of recursive DNS resolvers with that protocol, so percentages may overlap when one recursive DNS resolver supports several transports.

    DoUDP and DoTCP are conventional unencrypted DNS transports and are shown in two distinct pastel-red tones. Encrypted transports—including DoH, DoT, and DoQ variants—are shown in blue tones.
